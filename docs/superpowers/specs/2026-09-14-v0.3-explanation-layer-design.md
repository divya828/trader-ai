# v0.3 Design: Redaction Gate and Explanation Layer

Status: approved
Date: 2026-09-14
Builds on: [v0.2 Literature Metrics + Rule Engine](2026-09-13-v0.2-literature-metrics-design.md)

## Purpose

v0.2 produces typed, cited findings and a five-dimension health score, entirely
deterministically. v0.3 adds the explanatory tier: a hosted language model turns
those findings into prose a person can act on.

It is the first version in which anything leaves the machine on a per-run basis,
and therefore the version where the redaction gate stops being a design promise
and becomes enforced code.

## Non-negotiables (carried forward, with one amendment)

1. **Portfolio data stays local.** Holdings, amounts, folio numbers, and PAN
   never leave the machine. **Amended in v0.3:** an explanation call is made to
   a hosted model on every run, but it carries only redacted findings — no
   scheme names, no amounts, no identifiers. See The Amendment below.
2. **No execution.** No order-placement code path. Unchanged.
3. **Deterministic math is never delegated to an LLM.** Every number in an
   explanation was computed by v0.1/v0.2 code and passed to the model as input.
   The model may restate a number; it may never produce one.
4. **Hosted calls pass an explicit redaction gate,** enforced by the input type
   the hosted node accepts rather than by prompt wording. This is the version
   that implements it.

### The amendment

The original project brief specified a **local Qwen model via Ollama** on an
M1 Pro, scoped to tool-routing and narration. v0.3 instead uses a **hosted
Anthropic model, and no local model at all**.

This is recorded rather than absorbed silently, because it changes a stated
constraint. What makes it defensible is the pairing: the redaction is stricter
than the original brief required. Non-negotiable #4 asked only that position
sizes, amounts and folio numbers be stripped. Findings already contain none of
those. v0.3 additionally strips **scheme names**, which the brief did not
require — because a name plus a weight reveals which funds are held and in what
proportion, which is a portfolio disclosure even though no rupee figure appears.

So: every explanation call leaves the machine, and nothing identifying does.

If a local model is wanted later, `llm/client.py` is the only module that would
change; nothing above it knows where the text came from.

## Scope

In scope for v0.3:
- A redaction gate: `Finding` → `RedactedFinding`, with scheme identity replaced
  by opaque labels and the mapping retained locally.
- A hosted Anthropic client, the only module that performs network I/O or reads
  an API key.
- An explainer that prompts the model with redacted findings and parses the
  result.
- Local re-attachment of real names to the returned text.
- A report assembling findings, scores and explanations.
- Graceful degradation when the model is unreachable.

Out of scope, explicitly:
- Any local model (Ollama, Qwen, MLX).
- Tool-calling, agent loops, LangGraph, or any multi-step model orchestration.
- Model access to the ledger, the database, or any file.
- Letting the model compute, adjust, or infer any number.
- Order placement, in any form, as in every prior version.

## Measured facts

These were verified against the real 16-scheme ledger before this spec was
written, not assumed.

### Findings are already self-sufficient for explanation

A real finding carries its `rule_id`, severity, title, subjects (kind, ref,
weight), every number in `metrics`, and a citation resolving to a named source
and a specific claim. An explainer given this needs no ledger access: it has
both the figures and the authority behind the rule.

### Findings carry scheme names, and that is a disclosure

Subjects reference schemes by name, e.g. `HDFC BSE Sensex Index Fund - Direct
Plan - Growth` at 8.1%. Across the real portfolio's 4 findings there are 11
such subjects spanning 8 distinct funds. That is not amounts, folios or PAN —
the brief's stated redaction targets — but it is enough to reconstruct the
entire fund lineup and its proportions.

Explanations do not need it. "Three funds in one category, together 29% of the
portfolio, and here is why that matters" is fully comprehensible with opaque
labels. Names add specificity, not understanding, and are re-attached locally
after the response.

### Labels must key on scheme_id, not scheme name

A prototype gate keyed on scheme name **collapsed distinct holdings**. In the
real ledger, three names each map to two different `scheme_id` values — the
same fund held through two folios:

| Scheme name | scheme_ids |
|---|---|
| ICICI Prudential Technology Fund - Direct Plan - Growth | 2, 3 |
| quant Infrastructure Fund - Direct Plan - Growth | 11, 14 |
| ICICI Prudential Healthcare Fund - Direct Plan - Growth | 5, 6 |

Name-keyed labelling produced `fund_4` carrying two different weights in one
payload, which would have made the explanation wrong. The gate keys on
`scheme_id`, which never leaves the machine in any case.

### A redacted payload is verifiably clean

Serialising the real portfolio's findings through the gate produces a payload
containing no scheme names, no PAN-shaped strings, no real folio numbers, and
no rupee amounts, while retaining every metric and citation. With `scheme_id`
keying, the real portfolio's 4 findings yield 11 distinct labels and no label
carries two different weights.

### The payload scan must compare values, not shapes

A shape-based folio check (`\d{3,}/\d+`) produces a **false positive on a
citation**: `SEBI circular SEBI/HO/IMD/DF3/CIR/P/2017/114` contains `2017/114`.
That is a public regulation number, not a folio.

A test failing on it would invite someone to weaken the check — the worst
possible outcome for a guard whose whole job is to be strict. So the payload
scan asserts that **no actual value from the ledger** appears: it reads the real
folio numbers, masked PANs and scheme names from the database and asserts none
is present in the serialised request. That is stricter than a heuristic (it
catches any format) and has no false positives (the ledger knows its own
values). Real folios look like `20244566/ 39`, which no citation resembles.

## Architecture

```
src/trader_ai/
├── rules/                   # v0.2c, unchanged — produces Finding
└── llm/                     # NEW
    ├── redaction.py         # Finding -> RedactedFinding; owns the label map
    ├── client.py            # the ONLY module that performs network I/O
    ├── explainer.py         # prompt construction, response parsing
    └── report.py            # findings + scores + explanations -> output
```

### Dependency direction

```
rules  ->  llm.redaction  ->  llm.explainer  ->  llm.client  ->  Anthropic API
                 |                  ^
          label map (local)  -------+  names re-attached after response
```

Enforced rules, each asserted by test:

- `llm.client` accepts **only** `RedactedFinding`. It has no import path to
  `Finding`, to `rules.context`, to `ingest`, or to the database. Passing an
  unredacted finding is a type error, not a runtime check.
- `llm.client` is the only module in the project permitted to import the
  `anthropic` SDK or perform HTTP.
- Nothing in `llm/` imports `trader_ai.ingest` or opens the ledger.
- No module in `llm/` computes a portfolio figure. The model is given numbers;
  it never derives one.

## The redaction gate

```python
@dataclass(frozen=True)
class RedactedSubject:
    kind: str              # SCHEME | SECURITY | ASSET_CLASS | PORTFOLIO
    label: str             # "fund_1" — opaque, keyed on scheme_id
    weight: float | None   # a ratio in [0,1], never an amount

@dataclass(frozen=True)
class RedactedFinding:
    rule_id: str
    severity: str
    subjects: list[RedactedSubject]
    metrics: dict[str, float]
    citation_source: str
    citation_claim: str

@dataclass(frozen=True)
class Redaction:
    findings: list[RedactedFinding]
    labels: dict[str, str]   # label -> real ref. NEVER leaves the process.
```

What is removed and why:

| Removed | Reason |
|---|---|
| `title` | Rule titles embed scheme names and category strings verbatim |
| `Subject.ref` | Scheme name — a portfolio disclosure; replaced by a label |
| `computed_at` | A timestamp is a weak correlation handle and adds nothing |
| `citation_key` | Replaced by the resolved source and claim, which is what the model needs |

What is kept: `rule_id`, `severity`, every metric, portfolio weights as ratios,
and the citation's source and claim — so the model can explain with grounding
rather than invention.

**Labels are keyed on the subject's originating `scheme_id`** where one exists,
falling back to the ref only for `ASSET_CLASS` and `PORTFOLIO` subjects, whose
refs (`EQUITY`, `portfolio`) are not identifying.

To make that possible without fragile caller bookkeeping, `Subject` gains an
optional `local_id: int | None` field, set by rules from the `HoldingView.scheme_id`
they already hold. It is used solely as a redaction key and **has no counterpart
on `RedactedSubject`**, so it cannot reach a payload -- the outbound type simply
has no field to carry it. A prototype threading the mapping in as a side table
keyed on object identity worked but was brittle; putting the id on the subject
is a three-line change to each rule family and removes the whole class of
bookkeeping error.

**ASSET_CLASS refs are not redacted.** `EQUITY` and `DEBT` are category names,
not holdings. Redacting them would make explanations incomprehensible while
protecting nothing.

## Enforcement

Three mechanisms, in decreasing strength:

1. **The type signature.** `client.explain(findings: list[RedactedFinding])`.
   There is no overload accepting `Finding`. This is the mechanism the
   non-negotiable asks for: enforced by the input type, not prompt wording.
2. **A payload scan.** A test serialises the exact request body sent for the
   real portfolio's findings and asserts that no value read from the ledger --
   folio numbers, masked PANs, scheme names -- appears anywhere in it. Value
   comparison rather than shape matching, for the reason given above. This
   catches leaks through any field, including fields added later.
3. **Layering tests.** `llm/` may not import `ingest`; only `client.py` may
   import `anthropic` or `urllib`; no `llm/` module may compute a figure.

Each guard is verified to fail on an injected violation before being trusted —
the practice established in v0.2a and v0.2c.

## The model call

- **Model:** `claude-opus-5`.
- **Credentials:** read from the environment by the SDK's own resolution chain.
  No key is ever written to a file in this repo, and the repo's `.gitignore`
  already covers `.env`.
- **Prompting:** the system prompt states that every number is given and must
  not be recomputed, altered, or extrapolated; that labels are opaque and must
  be used verbatim; and that no investment advice is to be offered — the tool
  is advisory-only and explains findings rather than recommending trades.
- **Output:** one short explanation per finding, returned as structured output
  keyed by `rule_id` so responses cannot be silently misattributed.

## Failure behaviour

Bounded retry, then degrade — never fail the run.

The SDK retries connection errors, 429 and 5xx twice by default with
exponential backoff; that default is kept. After retries are exhausted, or when
no credential is configured, or when the response cannot be parsed, the report
renders the finding's own title, metrics and citation, and states that the
explanation was unavailable and why.

This mirrors how every v0.2 metric handles missing data: the deterministic layer
already produces the entire report, and the model is an enhancement, never a
dependency. A network blip must not destroy a report whose numbers were all
computed locally and correctly.

## Testing Strategy

- The redaction gate is tested against the **real ledger's findings**, not only
  synthetic ones. The `scheme_id` collision above was found that way and would
  not have surfaced otherwise.
- A fake client implements the same protocol as the real one, so the explainer,
  re-attachment and report are fully tested with no network and no API key.
- The payload scan runs on a serialised real request.
- Live model tests are opt-in behind an environment variable, as the AMFI live
  tests are, so the default suite stays hermetic, fast and free.
- Degradation is tested explicitly: missing key, connection error, exhausted
  retries, and unparseable response each produce a usable report.

## Out of Scope Confirmation

No local model. No tool-calling or agent loop. No model access to the ledger or
filesystem. No model-produced numbers. No order placement. The LLM receives
redacted findings and returns text; everything else remains deterministic.
