# v0.1 Design: Ledger Ingestion + Deterministic Analytics

Status: approved
Date: 2026-08-18

## Purpose

Build the foundation of a personal agentic investment harness for Indian mutual
funds and stocks. v0.1 proves that the ledger (ingested from eCAS PDFs) and the
core deterministic math (XIRR, allocation drift, tax lots) are correct — before
any LLM or agent logic is allowed to touch them.

This is advisory-only software. No component in this scope, or any future
scope, executes trades. That constraint is architectural, not a feature flag.

## Non-negotiables (carried from project brief, restated for this spec)

1. **Fully local.** Holdings, amounts, folio numbers, PAN never leave the
   machine or appear in a hosted/cloud API call. v0.1 has no network calls at
   all except reading local files, so this is trivially satisfied — but the
   repo/data layout must not create future temptation to violate it (see Data
   Storage below).
2. **No execution.** v0.1 contains no order-placement code path, full stop.
3. **Deterministic math is never delegated to an LLM.** v0.1 has no LLM calls
   at all. XIRR, tax lots, and allocation drift are plain, unit-tested Python.
4. **Redaction gate for any future hosted-model call.** Not applicable to
   v0.1 (no LLM calls exist yet), but the `ingest` / `analytics` boundary
   described below is designed so that boundary is easy to insert later.

## Scope

In scope for v0.1:
- Parse a sample eCAS PDF (via `casparser`) into normalized SQLite tables:
  folios, schemes, securities, demat accounts, transactions.
- Deterministic, unit-tested Python functions, callable directly (no LLM, no
  orchestration graph):
  - XIRR per fund/stock and portfolio-level.
  - Current allocation vs. a user-specified target, compared by **asset
    class** (Equity / Debt / Hybrid / Gold / Cash).
  - Tax lots via FIFO matching, with LTCG/STCG **classification only**
    (holding-period vs. asset-type threshold) — no tax amount, no exemption
    slab, no grandfathering computation.

Out of scope for v0.1 (explicitly deferred):
- LangGraph orchestration, any LLM call (local or hosted), redaction gate
  implementation, MVO/covariance optimizer, UI, broker API integration,
  actual tax liability computation.

## Ingestion Source Shape

Verified against `casparser==1.4.1` (API inspected directly, not assumed).

`casparser.read_cas_pdf(filename, password, output="dict")` returns **one of
two different types** depending on who issued the statement:

**`CASData`** — CAMS / KFintech issuers. Mutual funds with full history:
- `.investor_info` → `InvestorInfo(name, email, address, mobile)`.
  Note: **no PAN field here.**
- `.statement_period` → `StatementPeriod(from_, to)`
- `.folios[]` → `Folio(folio, amc, name, PAN, KYC, PANKYC, schemes[])`.
  **PAN lives on the folio**, and is masked before it touches the DB.
- `Folio.schemes[]` → `Scheme(scheme, rta_code, rta, type, isin, amfi,
  open, close, close_calculated, valuation, transactions[])`
- `Scheme.valuation` → `SchemeValuation(date, nav, cost, value)` — gives
  current NAV and value directly, so allocation needs no external price feed
  in v0.1.
- `Scheme.transactions[]` → `TransactionData(date, description, amount,
  units, nav, balance, type, dividend_rate, gift_folio)`

**`NSDLCASData`** — NSDL / CDSL issuers. Demat holdings, **snapshot only**:
- `.accounts[]` → `DematAccount(name, type, dp_id, client_id, folios,
  balance, owners[], equities[], mutual_funds[], bonds[])`
- `DematOwner(name, PAN)` — PAN masked before storage.
- `Equity(name, isin, num_shares, price, value, symbol, exchange)`

### Critical consequence: stocks have no transaction history

`Equity` is a point-in-time holding. casparser exposes **no buy/sell
transaction stream for stocks**. Therefore in v0.1:

| Tool | Mutual funds | Stocks |
|---|---|---|
| Allocation drift | Yes | **Yes** (uses holdings snapshot value) |
| XIRR | Yes | **Not computable** — no dated cashflows |
| FIFO tax lots | Yes | **Not computable** — no acquisition dates/costs |

Stock XIRR and stock tax lots are therefore **explicitly out of scope for
v0.1**, not by preference but because the data does not exist in this
source. The `transactions` schema still accommodates stock rows so a future
broker tradebook importer can populate them without a migration; until then
`securities` are valued from a holdings snapshot table.

The `ingest` layer's job is solely to map these into the normalized schema
below — it performs no analysis, and `analytics` code never imports from or
calls into `ingest`.

## Data Storage

- SQLite DB, raw PDFs, and any casparser intermediate output live under a
  gitignored `data/` directory inside the repo.
- `.gitignore` excludes `data/`, `*.db`, `*.pdf` at minimum.
- Tests use synthetic/dummy fixture PDFs and an in-memory SQLite DB — no real
  portfolio data is ever required to run the test suite.

Key structural decision: `ingest/` and `analytics/` are hard-separated with
no cross-imports. `ingest` is the only code that ever sees raw
PII-shaped data (folio numbers, PAN, amounts tied to identity). `analytics`
operates purely on normalized DB rows. This boundary is what makes a future
redaction gate straightforward to insert — it has exactly one place to sit
(between DB reads and any hosted call), and it's also why math functions can
be unit-tested with synthetic numbers, independent of ingestion.

No `orchestration/` or `llm/` directories exist yet; they are not created
until a later phase's design.

## SQLite Schema

```sql
-- Folios: one row per (AMC folio number) as reported in the CAS.
-- Mutual fund transactions/holdings nest under folios.
CREATE TABLE folios (
    folio_id        INTEGER PRIMARY KEY,
    folio_number    TEXT NOT NULL,
    amc             TEXT NOT NULL,          -- e.g. "HDFC Mutual Fund"
    pan_masked      TEXT,                   -- masked (e.g. "ABCXXX234Z"), never full PAN
    UNIQUE (folio_number, amc)
);

-- Schemes: one row per mutual fund scheme within a folio.
CREATE TABLE schemes (
    scheme_id       INTEGER PRIMARY KEY,
    folio_id        INTEGER NOT NULL REFERENCES folios(folio_id),
    amfi_code       TEXT,                   -- AMFI scheme code, nullable if unmatched
    isin            TEXT,
    scheme_name     TEXT NOT NULL,
    asset_class     TEXT NOT NULL DEFAULT 'UNCLASSIFIED'
                        CHECK (asset_class IN ('EQUITY','DEBT','HYBRID','GOLD','CASH','UNCLASSIFIED'))
);

-- NOTE: a table-level UNIQUE(folio_id, scheme_name, isin) does NOT dedupe
-- schemes whose isin is NULL (casparser types Scheme.isin as Optional), because
-- SQL treats every NULL as distinct. Such schemes would gain a duplicate row on
-- every re-import, inflating holdings. Two partial unique indexes cover both
-- cases -- the same NULL trap as holdings_snapshot below.
CREATE UNIQUE INDEX idx_schemes_isin_uniq
    ON schemes(folio_id, scheme_name, isin) WHERE isin IS NOT NULL;
CREATE UNIQUE INDEX idx_schemes_no_isin_uniq
    ON schemes(folio_id, scheme_name) WHERE isin IS NULL;

-- Securities: one row per stock (ISIN), held in demat — separate from MF schemes
-- because casparser reports these as holdings, not scheme transaction streams.
CREATE TABLE securities (
    security_id     INTEGER PRIMARY KEY,
    isin            TEXT NOT NULL UNIQUE,
    symbol          TEXT,
    name            TEXT NOT NULL,
    exchange        TEXT,                   -- NSE / BSE
    asset_class     TEXT NOT NULL DEFAULT 'EQUITY'
                        CHECK (asset_class IN ('EQUITY','UNCLASSIFIED'))
);

-- Demat accounts: analogous to folios, for stock holdings.
CREATE TABLE demat_accounts (
    demat_account_id INTEGER PRIMARY KEY,
    dp_id           TEXT NOT NULL,
    client_id       TEXT NOT NULL,
    depository      TEXT NOT NULL CHECK (depository IN ('CDSL','NSDL')),
    UNIQUE (dp_id, client_id)
);

-- Unified transaction ledger for BOTH mutual fund and stock transactions.
-- One table keeps XIRR/lot logic asset-type-agnostic (same shape, different FK populated).
CREATE TABLE transactions (
    transaction_id        INTEGER PRIMARY KEY,
    scheme_id             INTEGER REFERENCES schemes(scheme_id),
    security_id           INTEGER REFERENCES securities(security_id),
    demat_account_id       INTEGER REFERENCES demat_accounts(demat_account_id),
    txn_date               TEXT NOT NULL,      -- ISO 8601 'YYYY-MM-DD'
    -- Mirrors casparser.enums.TransactionType exactly (v1.4.1), so ingestion
    -- never has to lossily remap and never trips the CHECK on real data.
    txn_type                TEXT NOT NULL CHECK (txn_type IN (
                                'PURCHASE','PURCHASE_SIP','REDEMPTION',
                                'DIVIDEND_PAYOUT','DIVIDEND_REINVEST',
                                'SWITCH_IN','SWITCH_IN_MERGER',
                                'SWITCH_OUT','SWITCH_OUT_MERGER',
                                'STT_TAX','STAMP_DUTY_TAX','TDS_TAX',
                                'SEGREGATION','GIFT_IN','GIFT_OUT',
                                'MISC','UNKNOWN','REVERSAL'
                            )),
    units                    REAL,             -- signed: +buy, -sell (NULL for pure cash entries like STT)
    price                     REAL,             -- NAV for MF, trade price for stock
    amount                    REAL NOT NULL,    -- signed cashflow, always populated (used by XIRR)
    source_row_hash            TEXT NOT NULL UNIQUE,  -- hash of raw source fields; enforces idempotent re-import
    CHECK (
        (scheme_id IS NOT NULL AND security_id IS NULL) OR
        (scheme_id IS NULL AND security_id IS NOT NULL)
    )
);

CREATE INDEX idx_transactions_scheme ON transactions(scheme_id, txn_date);
CREATE INDEX idx_transactions_security ON transactions(security_id, txn_date);

-- Cost basis lots — populated/refreshed by the FIFO tax-lot tool, not by ingestion.
-- Kept as a derived table (not raw ledger) so it can be recomputed deterministically
-- from transactions at any time.
CREATE TABLE tax_lots (
    lot_id                 INTEGER PRIMARY KEY,
    scheme_id              INTEGER REFERENCES schemes(scheme_id),
    security_id            INTEGER REFERENCES securities(security_id),
    open_transaction_id    INTEGER NOT NULL REFERENCES transactions(transaction_id),
    acquired_date           TEXT NOT NULL,
    units_remaining          REAL NOT NULL,
    cost_per_unit             REAL NOT NULL,
    CHECK (
        (scheme_id IS NOT NULL AND security_id IS NULL) OR
        (scheme_id IS NULL AND security_id IS NOT NULL)
    )
);

-- Lot consumption record — which redemption consumed which lot, how many units,
-- and the resulting gain classification. This is the FIFO matching's audit trail.
CREATE TABLE lot_disposals (
    disposal_id             INTEGER PRIMARY KEY,
    lot_id                  INTEGER NOT NULL REFERENCES tax_lots(lot_id),
    close_transaction_id    INTEGER NOT NULL REFERENCES transactions(transaction_id),
    disposed_date            TEXT NOT NULL,
    units_disposed            REAL NOT NULL,
    cost_basis                 REAL NOT NULL,   -- units_disposed * lot.cost_per_unit
    proceeds                    REAL NOT NULL,
    gain                          REAL NOT NULL,
    holding_period_days             INTEGER NOT NULL,
    classification                    TEXT NOT NULL CHECK (classification IN ('STCG','LTCG'))
);

-- Point-in-time holdings snapshot, per import run.
-- This is how stocks get valued (they have no transaction stream), and it
-- also captures each scheme's reported NAV/value so allocation needs no
-- external price feed in v0.1.
CREATE TABLE holdings_snapshot (
    snapshot_id        INTEGER PRIMARY KEY,
    import_run_id      INTEGER NOT NULL REFERENCES import_runs(import_run_id),
    scheme_id          INTEGER REFERENCES schemes(scheme_id),
    security_id        INTEGER REFERENCES securities(security_id),
    as_of_date          TEXT NOT NULL,     -- ISO 8601
    units                REAL NOT NULL,    -- units (MF) or num_shares (stock)
    price                 REAL NOT NULL,   -- NAV (MF) or market price (stock)
    value                  REAL NOT NULL,
    cost                    REAL,          -- reported cost basis where available
    CHECK (
        (scheme_id IS NOT NULL AND security_id IS NULL) OR
        (scheme_id IS NULL AND security_id IS NOT NULL)
    )
);

-- NOTE: a table-level UNIQUE(import_run_id, scheme_id, security_id) does NOT
-- work here: SQL treats NULL as distinct from NULL, so rows with a NULL
-- security_id would never collide and re-imports would silently duplicate
-- holdings. Two partial unique indexes are required instead.
CREATE UNIQUE INDEX idx_holdings_snapshot_scheme_uniq
    ON holdings_snapshot(import_run_id, scheme_id) WHERE scheme_id IS NOT NULL;
CREATE UNIQUE INDEX idx_holdings_snapshot_security_uniq
    ON holdings_snapshot(import_run_id, security_id) WHERE security_id IS NOT NULL;

CREATE INDEX idx_holdings_snapshot_run ON holdings_snapshot(import_run_id);

-- Target allocation, specified per asset class.
CREATE TABLE target_allocation (
    asset_class      TEXT PRIMARY KEY CHECK (asset_class IN ('EQUITY','DEBT','HYBRID','GOLD','CASH')),
    target_weight     REAL NOT NULL CHECK (target_weight >= 0 AND target_weight <= 1)
);

-- Ingestion run log — tracks each casparser import for traceability/idempotency debugging.
CREATE TABLE import_runs (
    import_run_id                INTEGER PRIMARY KEY,
    source_file                    TEXT NOT NULL,
    imported_at                      TEXT NOT NULL DEFAULT (datetime('now')),
    cas_statement_period_start         TEXT,
    cas_statement_period_end             TEXT,
    rows_inserted                          INTEGER NOT NULL DEFAULT 0,
    rows_skipped_duplicate                   INTEGER NOT NULL DEFAULT 0
);
```

### Schema design notes

- **Unified `transactions` table** for both MF and stock activity (nullable
  `scheme_id` xor `security_id` via CHECK constraint). This lets `xirr.py`
  and `tax_lots.py` be single implementations that operate on cashflows/lots
  generically, rather than duplicating logic per asset type.
- **`source_row_hash`** is the idempotency mechanism: the ingest adapter
  computes a stable hash from casparser's raw row fields (folio/ISIN + date +
  amount + type) so `INSERT OR IGNORE` makes re-importing the same or
  overlapping-period PDF safe — no duplicate transactions, no double-counted
  XIRR or lots.
- **`tax_lots` and `lot_disposals` are derived, not raw ledger data.** They
  are wiped and recomputed from `transactions` each time the FIFO tool runs,
  so they can never drift out of sync with the source of truth.
- **`pan_masked`** — full PAN is never stored, even locally, by default.
- **`asset_class` defaults to `UNCLASSIFIED`** on schemes — casparser
  provides scheme names/ISINs but not a ready asset-class tag, so
  classification (e.g. via a static AMFI-category lookup) is a deliberate,
  separate step, not assumed at ingest time. The allocation-drift tool
  should treat `UNCLASSIFIED` holdings as visibly flagged, not silently
  excluded.

## Deterministic Tools (functions, not services)

All three are plain Python functions taking normalized data (either DB rows
or plain dataclasses) and returning plain data — no I/O side effects beyond
reading the DB, no LLM calls, no network calls.

1. **`xirr.py`** — Given a list of dated signed cashflows (+ current market
   value as a final synthetic inflow), returns the XIRR. Computed per
   **scheme** and aggregated at portfolio level. Stocks are excluded (no
   cashflow history exists — see Ingestion Source Shape). Must handle edge
   cases: empty input, single cashflow, all-same-sign cashflows (no
   solution → return `None` rather than raise), and verify against known
   reference values in tests. Implemented as bisection on NPV over a
   bracketed rate range, which is more robust than Newton-Raphson for the
   irregular cashflow patterns SIPs produce.
2. **`allocation.py`** — Given the latest `holdings_snapshot` rows joined to
   their asset class (schemes and securities both) and `target_allocation`
   rows, returns drift per asset class (current % − target %) plus flags any
   `UNCLASSIFIED` value found. Covers stocks and mutual funds alike.
3. **`tax_lots.py`** — Mutual funds only in v0.1 (stocks lack acquisition
   dates and costs). FIFO matches each disposal (REDEMPTION / SWITCH_OUT /
   SWITCH_OUT_MERGER / GIFT_OUT) against open lots in acquisition order,
   where acquiring types are PURCHASE / PURCHASE_SIP / SWITCH_IN /
   SWITCH_IN_MERGER / DIVIDEND_REINVEST / GIFT_IN. Splits lots as
   needed, and classifies each resulting disposal as STCG or LTCG purely by
   holding period vs. a per-asset-type threshold: equity MF/stock use 365
   days. Debt MF units acquired before 2023-04-01 use 1095 days (old
   indexation-era rule). Debt MF units acquired on or after 2023-04-01 are
   always classified `STCG` regardless of holding period, per the current
   slab-rate regime — this fits the existing `STCG`/`LTCG` schema values
   without a third label. No tax amount, exemption slab, or grandfathering
   is computed in v0.1.

## Testing Strategy

- `tests/fixtures/sample_ecas.pdf` — a synthetic CAS PDF (fabricated
  holdings/transactions, not real data) used to validate the full
  ingest → schema pipeline end to end.
- Each analytics module has unit tests with hand-computed expected values
  (XIRR verified against a known reference calculator; FIFO lots verified
  against manually traced examples; allocation drift against simple
  arithmetic cases).
- `conftest.py` provides an in-memory SQLite DB with `schema.sql` applied,
  so tests never touch `data/ledger.db`.
- Idempotent re-import is itself tested: importing the same fixture PDF
  twice must not change `transactions` row count.

## Out of Scope Confirmation

No LangGraph, no LLM (local or hosted), no MVO/covariance optimizer, no UI,
no broker/execution API. v0.1 ends at: importable, correct ledger +
independently callable, correct, unit-tested math functions.
